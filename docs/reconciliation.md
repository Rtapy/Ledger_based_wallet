# تصمیم‌های تطبیق موجودی و Ledger

تابع `wallet.reconciliation.reconcile_wallet(user_id=...)` و فرمان
`manage.py reconcile_wallet --user-id ID` فقط داده را بررسی می‌کنند؛ موجودی، تاریخچه
و timestampها را تغییر نمی‌دهند. مغایرت نتیجهٔ قابل گزارش است، نه مجوز اصلاح خودکار.

## چه چیزی بررسی می‌شود؟

۱. PostgreSQL جمع مبلغ creditها منهای مبلغ debitها را از صفر محاسبه می‌کند؛
این عدد با `Wallet.balance` مقایسه می‌شود. جمع‌زدن `balance_after`ها یا تکیه بر
آخرین رکورد جایگزین این محاسبه نیست. جمع در SQL محاسبه می‌شود تا دقت Decimal
فرایند پایتون، مجموع بزرگِ یک تاریخچهٔ خراب را گرد نکند.

۲. رکوردها به ترتیب ID بررسی می‌شوند: اولین before باید صفر باشد، before هر رکورد
با after قبلی برابر باشد و محاسبهٔ همان رکورد با نوع و مبلغش سازگار باشد.
بازهٔ مبلغ و موجودی هم بررسی می‌شود. نتیجه فقط وقتی صحیح است که **هم جمع و هم زنجیره**
درست باشند؛ ممکن است جمع نهایی درست بماند ولی snapshotهای میانی خراب شوند.

۳. `first_invalid_entry_id` اولین جایی است که ناسازگاری زنجیره مشاهده شده، نه لزوماً
رکوردی که عامل اولیهٔ خرابی بوده است. مثلاً بعد از حذف یک رکورد میانی، شکست در رکورد
بعدی دیده می‌شود. جمع و تعداد همچنان مربوط به تمام Ledger آن کیف پول هستند.

## سازگاری در هم‌زمانی

پیش از خواندن موجودی، تابع داخل `transaction.atomic()` روی همان Wallet که سرویس
posting قفل می‌کند، `select_for_update()` می‌گیرد. قفل تا پایان جمع‌زدن و بررسی زنجیره
حفظ می‌شود. در تنظیم فعلی PostgreSQL با READ COMMITTED، اگر posting جلوتر باشد،
تطبیق بعد از commit یا rollback آن، وضعیت نهایی را می‌خواند. اگر تطبیق جلوتر باشد،
posting روی همان کیف پول منتظر می‌ماند؛ کیف پول‌های دیگر قفل نمی‌شوند.

این تضمین به رعایت قرارداد قفل توسط تمام نویسنده‌ها وابسته است. SQL یا ORM مستقیمی
که Ledger را بدون قفل Wallet تغییر دهد، جزو این تضمین نیست. اگر تابع داخل تراکنش
بیرونی فراخوانی شود، قفل تا پایان همان تراکنش بیرونی باقی می‌ماند.

## هزینه و محدودیت

تطبیق کامل O(n) است و در طول بررسی، نوشتن روی کیف پول هدف منتظر می‌ماند. رکوردهای
زنجیره با `iterator(chunk_size=1000)` خوانده می‌شوند تا تمام تاریخچه در حافظه جمع نشود.
این انتخاب برای فرمان مدیریتی این پروژه است؛ تاریخچهٔ حجیم می‌تواند به اجرای زمان‌بندی‌شده
یا طراحی تطبیق مرحله‌ای نیاز داشته باشد. خواندن عادی تاریخچهٔ API همچنان قفل نمی‌گیرد.

این مقایسه نمی‌تواند بازنویسی هماهنگ همهٔ رکوردها و موجودی را تشخیص دهد؛ دفتر مالی
هنوز در برابر ویرایش مستقیم اپراتور دیتابیس immutable نشده است.

## خروجی و آزمون

تابع، `ReconciliationResult` با Decimal برمی‌گرداند. فرمان همان گزارش را به JSON
با مبالغ رشته‌ایِ هشت‌رقمی تبدیل می‌کند: موجودی صحیح کد خروج ۰ دارد؛ مغایرت بعد از
چاپ گزارش با `CommandError` و کد خروج ۱ اعلام می‌شود. شناسهٔ نامعتبر یا کاربر/کیف پول
ناموجود نیز خطاست؛ هیچ موجودیتی خودکار ساخته نمی‌شود.

۲۴ تست این مرحله پاس شدند: کیف پول خالی، اعشار و مرز مبلغ، تغییر موجودی، خرابی
زنجیره با جمع صحیح، حذف رکورد میانی، جمع بزرگ‌تر از ظرفیت یک فیلد، جداسازی کیف پول‌ها،
عدم تغییر داده‌ها و خروجی فرمان. چهار تست هم‌زمانی با PostgreSQL، اتصال مستقل و
مشاهدهٔ واقعی `pg_blocking_pids` یا تکمیل نوشتن روی کیف پول دیگر اجرا شدند.
در دو تست، posting دقیقاً میان ذخیرهٔ موجودی و درج Ledger متوقف می‌شود تا انتظار
تطبیق و نتیجهٔ صحیح پس از commit و rollback بررسی شود.
