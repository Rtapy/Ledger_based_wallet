# تصمیم‌های مهندسی API برای ریویو

وضعیت: چهار قابلیت افزایش، کاهش، موجودی و تاریخچه پیاده شده‌اند. در تاریخ
۲۰۲۶-۰۹-۱۵ کل ۹۲ تست روی PostgreSQL پاس شدند؛ ۲۵ تست متعلق به لایهٔ API هستند.

## ۱. مرز مسئولیت‌ها

- serializer ورودی HTTP را اعتبارسنجی و به Decimal و UUID تبدیل می‌کند.
- view فقط ورودی معتبر را به `post_entry` می‌دهد و خروجی را serialize می‌کند.
- سرویس مسئول قفل، idempotency، محدودیت مالی و تراکنش است. منطق مالی در view تکرار نشده است.
- دو عملیات نوشتن، یک view پایه دارند و نوع عملیات را کلاس credit/debit مشخص می‌کند؛
  کلاینت نمی‌تواند نوع عملیات یا کیف پول را با فیلد اضافی در body عوض کند.
- خواندن موجودی و تاریخچه قفل نوشتن نمی‌گیرد؛ هر پاسخ، وضعیت مشاهده‌شده در زمان query است.

## ۲. اعشار و اعتبارسنجی پیش از quantize

**مسئولیت quantize کردن مقدار به دقیق ۸ رقم اعشار، قبل از فراخوانی سرویس، بر عهده‌ی caller (لایه‌ی API) است**

ابتدا ساختار رشته، تعداد اعشار، مثبت‌بودن و سقف مبلغ بررسی می‌شود، سپس quantize انجام
می‌شود. بنابراین `"1.000000000"` رد می‌شود؛ آن را با گردکردن به ورودی معتبر تبدیل نمی‌کنیم.
`"10"` و `"00010.1"` پذیرفته و به‌ترتیب به `10.00000000` و `10.10000000` تبدیل می‌شوند.
JSON number، نماد علمی، فاصله، علامت مثبت/منفی، ارقام فارسی/عربی و NaN/Infinity رد می‌شوند.
دقت context برای تبدیل، محلی تعیین می‌شود و float وارد محاسبات نمی‌شود.

خروجی تمام مبلغ‌ها رشته با دقیقاً ۸ رقم اعشار است؛ `entry_type` داخلی با نام `type`
منتشر می‌شود. از [DecimalField در DRF](https://www.django-rest-framework.org/api-guide/fields/#decimalfield)
برای نمایش خروجی استفاده شده است؛ ورودی سخت‌گیرانهٔ قراردادی فیلد جداگانه دارد.

## ۳. تشخیص کاربر و معنای جداسازی داده‌ها

تصمیم قبلیِ محیط ارزیابی حفظ شده: `AllowAny` و `authentication_classes = []`.
مسیر URL، کاربر هدف را انتخاب می‌کند. موجودی، تاریخچه، شمارش pagination و تغییرات مالی
همگی به کیف پول همان کاربر محدودند؛ کلید یکسان در دو کیف پول مستقل است.

**این جداسازی query است، نه کنترل دسترسی:** هر درخواست‌کننده می‌تواند user_id دیگری
را انتخاب کند. تست ورود کاربر دوم هم عمداً این محدودیت را نشان می‌دهد. برای استفاده
واقعی، احراز هویت و اثبات مالکیت پیش از دسترسی به کیف پول لازم است؛ در این مرحله اضافه نشده‌اند.
کاربر یا کیف پول ناموجود پاسخ ۴۰۴ می‌گیرد و API آن‌ها را خودکار ایجاد نمی‌کند.

## ۴. خطاها و اولویت بررسی

`WalletError` اکنون `code` و `message` دارد. handler مختص viewهای کیف پول، خطاهای سرویس
و DRF را به قالب `{"error":{"code":"...","message":"..."}}` تبدیل می‌کند.
جدول کامل کدها در README است. وضعیت‌های ۴۰۰، ۴۰۴، ۴۰۹، ۴۰۵، ۴۰۶ و ۴۱۵ تفکیک شده‌اند.
خطای غیرمنتظره در لاگ داخلی ثبت می‌شود و پاسخ ۵۰۰ متن عمومی دارد، حتی وقتی DEBUG روشن باشد.

در POST، پس از بررسی method و content negotiation، ابتدا body و سپس هدر کلید بررسی
می‌شود؛ سرویس بعد از آن وجود کیف پول، retry/conflict و محدودیت موجودی را بررسی می‌کند.
وقتی چند ایراد هم‌زمان وجود داشته باشند، این ترتیب تعیین‌کنندهٔ خطای پاسخ است.
بدنهٔ فاقد amount یا دارای فیلد اضافه `invalid_request` می‌گیرد؛ مقدار نامعتبرِ amount
کد `invalid_amount` می‌گیرد. کلید JSON تکراری رد می‌شود تا انتخاب ضمنی آخرین amount رخ ندهد.

handler با سازوکار [مدیریت خطای DRF](https://www.django-rest-framework.org/api-guide/exceptions/#custom-exception-handling)
به view پایه متصل است؛ تنظیمات admin را تغییر نمی‌دهد. خطای routing در URL ناموجود
و خطاهای middleware بیرون از این handler هستند. اطلاعات SQL و traceback در پاسخ API منتشر نمی‌شوند.

## ۵. تاریخچه و pagination

ترتیب صعودی ID صریح است. `limit` پیش‌فرض ۲۰ و حداکثر ۱۰۰ است؛ `offset` پیش‌فرض صفر است.
پارامتر نامعتبر یا تکراری و پارامتر ناشناخته، ۴۰۰ می‌گیرد؛ مقدار نامعتبر به‌صورت خاموش
به پیش‌فرض تبدیل نمی‌شود. offset بزرگ‌تر از تعداد رکوردها results خالی می‌دهد.
count و لینک‌های بعد/قبل متعلق به همان user_id هستند.

از [LimitOffsetPagination](https://www.django-rest-framework.org/api-guide/pagination/#limitoffsetpagination)
با اعتبارسنجی سخت‌گیرانه‌تر استفاده شده است. این صفحه‌بندی snapshot ثابت نیست؛ count
و results در queryهای جدا خوانده می‌شوند و ممکن است هنگام درج هم‌زمان، وضعیت لحظه‌ای
متفاوتی ببینند. برای این پروژه قفل‌کردن نوشتن‌ها صرفاً برای تاریخچه انتخاب نشده است.

## ۶. retry و شکست

ثبت جدید ۲۰۱ و replay برابر ۲۰۰ است. replay دقیقاً رکورد تاریخی قبلی را برمی‌گرداند،
نه موجودی فعلی. شکست بین تغییر موجودی و درج Ledger، از مسیر API نیز rollback می‌شود؛
کلید آن درخواست برای تلاش بعدی آزاد می‌ماند. خطای دیتابیس به موفقیت یا replay تبدیل نمی‌شود.
درخواست با نتیجهٔ نامعلوم، مثلاً قطع اتصال پس از commit، باید با همان کلید تکرار شود.

## موارد باقی‌مانده

- reconciliation و تست تشخیص خرابی موجودی/زنجیره هنوز پیاده نشده‌اند.
- فرمان ساخت کاربر آزمایشی هنوز آماده نیست؛ README روش shell و نمونه‌های curl دارد.
- تست‌ها از Django/DRF APIClient با URL واقعی و PostgreSQL استفاده می‌کنند؛ اجرای
  مرورگر، reverse proxy یا آزمون بار شبکه‌ای جزو این تأیید نیست.
- این تغییرات آمادهٔ ریویو هستند و هنوز کامیت نشده‌اند.
